# Verbalist architecture

## Scope and delivery plan

1. **Foundation (implemented):** verified accounts, private profiles and preferences, text Quick Debate, motion library/generation, hybrid providers, autosaved drafts, resumable history, export/deletion, themes, tests.
2. **Voice (implemented locally):** browser microphone permissions and transcription, playback, text streaming, WebSocket revision notifications, synchronized practice clocks and recovery. Optional per-take local recording/download, off by default. No audio server, cloud audio storage or provider-native realtime speech.
3. **Intelligence (implemented locally):** typed/transcript-grounded argument snapshots, React Flow maps, potential-fallacy findings, optional OpenAI native research, advisory Quick Debate ballots, separate coaching, five drills, Recharts trends and activity achievements. External model/research quality remains unverified.
4. **Multiplayer (implemented locally):** invitation-only rooms, synchronized human turns/voice, independent judges, moderation, reviewed practice standings, private tournaments and advisory ballots. Public-network TURN/hardware checks remain external.
5. **MUN (requires explicit authorization):** committees, delegates, researched country positions, caucuses, negotiation, resolutions, amendments and advanced formats.

## Boundaries

`apps/web` is a Next.js App Router application with React, TypeScript, Tailwind and shadcn/ui primitives. `apps/api` is an independently deployable FastAPI application with validated REST contracts. `packages/shared-types` contains frontend API contracts. PostgreSQL is authoritative; no browser-only debate history or guest authentication exists. Supabase owns passwords, verification, OAuth and session rotation.

The browser authenticates through Supabase's cookie-based SSR client. Next.js verifies identity before rendering protected routes. API requests carry the user's access token; FastAPI verifies it with Supabase Auth on every request and forwards it to PostgREST. Ordinary requests never use a privileged database key. RLS restricts all private rows. Only account deletion uses the API-only secret key.

## Database and consistency

Phase 1 creates profiles, user_preferences, debate_formats, debate_sessions, debate_participants and debate_turns. Account creation provisions profile/preferences through a database trigger. Formats are versioned JSON configurations, with only Quick Debate enabled. Participants have stable identities to support future human rooms. Session and draft writes use compare-and-swap versions; serialized database functions validate ownership, turn order, status and replay identifiers. An interrupted AI request leaves the human turn saved, and the user can retry the outstanding AI turn. Every committed turn is immutable.

Drafts save after a short idle interval. A separate draft version detects edits from another device without conflating typing with transcript changes. Conflicts preserve local text and offer explicit recovery. A private authenticated WebSocket emits revision metadata; the browser then reloads authorized REST data. Exponential reconnect/backoff, focus refresh and periodic polling support recovery. Socket identity is reverified every 30 seconds and ownership checked every two seconds. This transport does not contain audio or transcripts.

Phase 2 adds speech preferences and persisted practice clocks. PostgreSQL owns clock phase, remaining milliseconds, start timestamp and session version. Pause freezes elapsed time and resume preserves the remainder. Clients derive the display using API server-time offset; database/client clock drift remains possible across infrastructure. Speaking must be started before a timed human turn is submitted. Expiry stops browser capture but allows transcript review, editing and later submission. Existing debates remain untimed.

## AI and credentials

Adapters cover OpenAI Responses, Anthropic Messages, Gemini generateContent, OpenAI-compatible endpoints and local compatible servers. Phase 2 adds their text SSE protocols and keeps standard requests as fallback. Provider completion, text/byte limits and atomic version checks must pass before an AI turn is saved. Cancellation or an incomplete stream leaves no partial turn; reload resolves the narrow race between commit and delivery. Native provider speech/structured capabilities remain unavailable; browser speech is a separate capability.

Browser recognition sends finalized text to the existing versioned draft path, displaying interim text separately. Speech synthesis reads committed responses in bounded chunks with pause/resume/cancel and a speaking allowance. Microphone processing requires explicit consent and permission; recognition and some voices may use browser-vendor online services. Local text inference does not imply local speech. Text fallback always remains available. WebRTC is unnecessary without a peer audio connection.

Audio saving is an independent per-take opt-in, initially off. Only an opted-in take creates a MediaRecorder. Its bounded file remains in page memory, available for local preview/download/discard. No recording flag, file, blob URL or speech consent is stored in Supabase or sent to the API. Navigation guards warn about unsaved files, but forced exit/device loss can lose them.

BYOK uses a stateless alternative to a server credential vault: the authenticated app's React context holds the key in memory and sends it over HTTPS in an `X-AI-Key` header on each provider request. FastAPI forwards it to the selected allowlisted provider and drops it at the end of the request. Keys never enter PostgreSQL, cookies, local/session storage, URLs, errors or analytics. Reload, logout, account change and the Clear credentials action erase browser-held keys. HTTP/APM infrastructure MUST redact Authorization and X-AI-Key and disable request header/body capture. Do not deploy behind infrastructure that records them. This design supports independent serverless workers without shared secret persistence.

Compatible/local endpoints are configured by the server operator, never supplied as arbitrary request URLs. Local inference is opt-in and only reaches the API host's configured server. A hosted API cannot access a user's laptop through localhost. Cloud endpoint redirects are disabled. Mock AI requires an explicit nonproduction flag and is visibly marked as simulated.

## Security and limits

Phase 3 adds `analysis_runs`, `arguments`, `argument_links`, `judge_ballots`, `feedback_reports`, `factual_claims`, `evidence_sources`, `practice_drills`, `drill_attempts`, `user_progress` and `achievements`. The shared drill catalog is read-only. All personal tables have ownership RLS, explicit SELECT grants, revoked direct writes and cascade paths. Composite run/session/owner and graph-edge keys prevent cross-session relationships. Mutation RPCs verify the caller and serialize relevant parent rows.

Analysis is on demand over immutable saved turns. Provider text must parse against strict Pydantic JSON models. Exact quote/speaker/turn grounding occurs in Python, and SQL independently validates excerpt positions before saving a whole run. Reference offsets use Unicode code points. A stale source version rejects the entire write. Separate ballots and coaching reports retain provenance; previous runs remain available through an owner-checked run identifier and export. Ballot arithmetic is server-derived. Delivery remains null. See [quick-v1](quick-debate-rubric.md).

Native research is a separate, explicit OpenAI BYOK request with a required web-search tool. The application does not fetch arbitrary source URLs. Only completed native search metadata with usable public HTTPS URL citations allows a non-unverified assessment. Citations establish source provenance, not semantic truth. Current claim assessment/model/time and latest citations are versioned together; rechecking replaces those current citations. Basic analysis never pretends to have researched a claim.

Drill submissions carry replay identifiers and exact response quotations. Progress is recomputed on each `learning_progress` RPC and cached in `user_progress`; exports may contain an older cache until refresh. Latest eligible evaluation per debate prevents rerun inflation. Chart links select the exact scored run. Mock reviews/drills remain stored but excluded from performance aggregates. Four achievements derive from actual saved practice; no competitive ranking is created.

Body/field limits, bounded transcript context, timeouts, safe provider error mapping, restrictive CORS, no raw HTML rendering, ownership RLS, and database-backed per-user rate budgets protect the application. Database functions use fixed search paths and explicit execute grants. All debate content is untrusted user data, never privileged instructions. Provider prompts separate policy from transcript and prohibit fabricated evidence; model compliance is imperfect and output remains unverified.

The deletion workflow requires a recent authenticated session, explicit confirmation, global session revocation and then Auth admin deletion. API identity checks reject deleted accounts even while old JWTs remain cryptographically valid. Foreign-key cascades remove account data. Public profiles and rankings are disabled in Phase 1.

## Infrastructure and validation constraints

Phase 4 adds a separate multiplayer domain rather than weakening solo session ownership. `debate_rooms` and `tournaments` inherit reads through verified active membership or event entry. The API continues forwarding each user's token; definer RPCs use fixed empty search paths and explicit grants. Invitation codes have 256 bits of entropy; only their SHA256 hashes are stored. Role occupancy, room capacity, expiration, revocation, full-roster seeding, clocks, speech order, replay and final result writes are serialized in PostgreSQL. Draft versions remain author-private and independent from shared room versions. A safe readiness retry handles changes to the other player's flag; consequential commands still reject stale versions.

An origin-checked authenticated socket carries version/presence notices and a bounded recipient-only SDP/ICE mailbox. No audio bytes travel through it. Native WebRTC uses a deterministic offerer, perfect-negotiation safeguards, ordered per-peer signaling, connection UUIDs, queued early ICE and explicit audio opt-in. The honest client gates sending and playback to the current unmuted speaker, and stops tracks/peers on disconnect, suspension or room end. Clients could modify their own software; floor/mute controls are practice controls, not an adversarial media-security boundary. Removed members lose server reads and signaling immediately, and compliant peers close them on the next presence tick. A dedicated media server is not implemented. TURN credentials come from operator configuration; no public relay is silently selected.

Only own-microphone MediaRecorder data can enter the optional local take. Each take is explicitly armed, off by default, bounded to 25 MB and held in page memory. Dictation never submits text automatically. Preview/download/discard are local; navigation guards cover app links and unloading, but forced exit/device loss can lose files. Server-side ballots use only committed text and exact two-speaker excerpt checks. A completed transcript cannot change; a ballot retains its source version while later room metadata revisions notify members. Only an independent judge can confirm an immutable written result. Bilateral room consent and global opt-ins gate unique per-result credit rows; simulated AI-assisted results are excluded. Event matches advance only in the human-confirmed result transaction.

Account exports include the caller's accessible shared records and only their own private drafts/ranking ledger. Invite secrets and transient networking data are excluded. Deletion removes any containing event and any room in which the account participated, with shared transcripts, ballots/results and derived credits. The before-delete Auth trigger deliberately enforces this for all members; deletion UI states that effect. This privacy-first deletion policy is more disruptive than anonymous transcript retention.

Frontend: Vercel-compatible standard Next.js build. Backend: ASGI deployment using the included container or any Python host. Supabase needs a project (or local Docker stack), enabled email confirmation, configured SMTP, Google credentials and redirect allowlists. No paid AI is required: use a separately installed local model server or explicit mock adapter for tests/development. Production rate limiting is shared via PostgreSQL; no process-local credential cache or rate state is required.

Live email delivery, Google consent, cross-device browser cookies and real provider calls require configured external infrastructure. Automated mocks cannot establish those claims. Database security tests run against a dedicated local Supabase test stack and must never target production.
